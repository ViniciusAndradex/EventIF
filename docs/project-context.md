CONTEXTO MESTRE — EventIF (autoridade para este projeto)

Objetivo: sistema web acadêmico para divulgar eventos, inscrições em atividades, presença e certificados. É uma atividade da disciplina Tópicos em Java para a Web; entregar repositório, README reprodutível, vídeo de até 10 minutos e tag final. Não ampliar o escopo.

Tecnologias obrigatórias: Java 21; Spring Boot 3.5.16 (linha 3.x exigida no enunciado; não usar 4.x); Spring MVC com Thymeleaf renderizado no servidor, não SPA/React; Spring Data JPA/Hibernate; Spring Security 6 com formulário; PostgreSQL; Maven; Git; Dockerfile e Docker Compose; Bootstrap 5 local; application.yml; Hibernate ddl-auto=update. EX03 é OpenHTMLtoPDF. Não usar Flyway, Lombok, MapStruct ou dependências sem necessidade.

Organização: pacote br.edu.ifce.eventif; Layered Architecture controller → service → repository. Controllers não acessam repository nem contêm regras. Services aplicam regras e transações. DTOs recebem formulários e Bean Validation. Código (classes, métodos, atributos) em inglês; telas, mensagens e rotas em português. GET consulta/página, POST cria, PUT atualiza/ações de estado, DELETE remove; habilitar HiddenHttpMethodFilter para formulários. Recursos em plural e subrecursos quando fizer sentido.

Entidades JPA — exatamente 6: User(id,name,email único,password BCrypt,active), Role(id,name), Category(id,name), Event(id,title,description,location,startDate,endDate,status), Activity(id,title,type,instructor,startDateTime,endDateTime,workloadMinutes Integer,capacity) e Enrollment(id,dateTime,present). User e Role são ManyToMany. Cada usuário tem exatamente um papel funcional exclusivo: ROLE_PARTICIPANTE, ROLE_ORGANIZADOR ou ROLE_ADMIN. Event pertence a Category e a User organizador; contém Activities. Activity pertence a Event e contém Enrollments. Enrollment pertence a User e Activity, com unicidade (user_id,activity_id). Enums persistem como String; EventStatus DRAFT/PUBLISHED/CLOSED e ActivityType LECTURE/MINICOURSE/WORKSHOP podem ser apresentados em português. Certificate não é entidade.

Requisitos funcionais: cadastro público cria PARTICIPANTE; login/logout; ADMIN faz CRUD de categorias e lista usuários, concede/retira ORGANIZADOR; ORGANIZADOR gerencia exclusivamente seus eventos e atividades, publica/encerra, lista inscritos e marca presença; catálogo público mostra PUBLICADOS paginados e filtra categoria; detalhe mostra atividades e vagas; PARTICIPANTE inscreve, cancela, vê suas inscrições/presenças e certificado. Layout em fragments, formulário th:object/th:field com erro por campo, flash messages. Seed idempotente: 2 categorias, 2 eventos com atividades e um usuário de cada perfil, incluindo ADMIN.

Segurança: SecurityFilterChain, UserDetailsService por email, BCrypt. Públicas: /, /eventos/**, /cadastro, /login. /organizador/** exclusivamente ORGANIZADOR; /admin/** exclusivamente ADMIN; restantes autenticadas. /admin e /organizador são obrigatórios pelo RS04, ainda que tecnicamente roles bastem; /participante não existe. Inscrições/certificados usam usuário da sessão. Trocar URL para evento/atividade de outro organizador retorna 403. Menus por sec:authorize são apenas interface, nunca segurança.

Regras RN01–RN07: email único; Event endDate >= startDate e Activity endDateTime > startDateTime, dentro do período inclusivo do evento; inscrição apenas em evento PUBLISHED; não duplicar inscrição; não ultrapassar capacidade; cancelar somente antes do início; certificado somente para CLOSED e ao menos uma presença.

Decisões finais adicionais: eventos nascem DRAFT. Publicar exige ao menos uma atividade. Editar eventos e atividades é permitido em DRAFT/PUBLISHED, nunca CLOSED. Encerramento manual apenas de PUBLISHED e não há reabertura. Excluir evento DRAFT/PUBLISHED apenas sem dependências; CLOSED nunca. Excluir Activity só sem inscrições e, em evento PUBLISHED, jamais a última atividade. Ao retirar ORGANIZADOR: bloquear se houver PUBLISHED; se houver só DRAFT, encerrá-los e depois retirar papel; ADMIN não é alterado por esse fluxo. workloadMinutes é calculado a partir do início e término da atividade, em minutos inteiros positivos, e persistido; o formulário não solicita carga separada. Reduzir capacidade abaixo de inscritos é proibido. Não usar cascata destrutiva.

Tempo: antes de Activity começar, inscrição e cancelamento permitidos, presença bloqueada. Durante, inscrição permitida se houver vagas, cancelamento bloqueado e presença permitida. Após término, os três bloqueados. Evento CLOSED bloqueia toda alteração, inscrição, cancelamento e presença. Por decisão do usuário, o projeto acadêmico prevê um ou no máximo dois usuários e não usa locks explícitos; operações simultâneas podem ultrapassar a capacidade ou invalidar outras verificações. Use Clock injetável quando a lógica temporal precisar dele.

Catálogo: somente PUBLISHED, 9 itens por página, filtro opcional por categoria, startDate ascendente e id ascendente como desempate; DRAFT/CLOSED no catálogo retornam 404. Vagas restantes e inscritos são calculados, não persistidos.

Certificado: página HTML imprimível e PDF OpenHTMLtoPDF para usuário autenticado elegível; nome, evento e soma das cargas das atividades com presença.

Testes: EX04 usa JUnit 5 e Mockito, sem PostgreSQL. Automatizar exclusivamente: RN01 em UserService; RN02 em EventService e ActivityService; RN04 em EnrollmentService. Não criar testes automatizados para RN03, RN05, RN06, RN07, concorrência, controllers, segurança ou PDF. As demais regras são verificadas manualmente e registradas; proteção contra concorrência está fora do escopo.

Entrega: README explica Docker Compose primeiro, alternativa Maven, URL, env, pré-requisitos, credenciais dos três perfis, estrutura, extras e pendências; .gitignore sem target/build/.idea/segredos. Vídeo mostra fluxos dos perfis, 403 por URL alterada, entidades, segurança e services. Não criar issue, commit, tag, release ou vídeo sem pedido explícito.
